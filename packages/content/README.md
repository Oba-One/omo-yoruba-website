# @oy/content

The content model and everything that reads or writes it: the Sanity schema and Studio, the GROQ
queries and their generated types, the Pending registry, the enquiry kinds spec, the seed, the
migrations and the two Sanity Functions. GROQ lives only here and in the root Blueprint manifest.
The site and the component library import the plain modules by subpath (`@oy/content/queries`,
`@oy/content/routes` and the others in `package.json`).

## What lives where

- `src/schema/`: the types, in `objects/`, `singletons/` (`siteSettings` and the twelve page
  singletons, each through `definePage`) and `documents/`.
- `src/studio/`: the Studio's configuration, sidebar, To do view, Presentation and roles, which
  `packages/web` mounts at `/admin`. The Sanity CLI loads it through `sanity.config.ts`, and
  `sanity.cli.ts` holds the schema extraction and TypeGen settings (ADR 0017).
- `src/queries/`: every query the site runs, each page in one read, typed by TypeGen.
- `src/pending.ts`: the Pending registry (ADR 0014) behind the site's chips and the Studio's To do.
- `src/enquiry-kinds.ts`: the one spec of the eight enquiry kinds and the newsletter (ADR 0007);
  `src/enquiry-zod.ts` derives the action schemas from it.
- `src/routes.ts`: the public routes and the types each reads, the one map behind the Presentation
  locations, the cache tags and the webhook purge.
- Plain modules that never import the Studio (`sanity`), shared by the schema, the seed and the site: layout options
  (`layout-options.ts`, `layout.ts`), which edition a page shows (`lead-event.ts`), the ways in,
  doors, other ways to give and albums (`take-part.ts`, `doors.ts`, `giving.ts`, `albums.ts`), image
  URLs and the stega filter (`images.ts`, `stega.ts`, ADR 0022), and what the Studio shows or hides
  (`edition-fields.ts`, `hidden-inputs.ts`, `scopes.ts`).
- `src/validation/`: the voice rules as Sanity validation, reusing `@oy/lint`.
- `src/sanity.types.ts` and `schema.json`: generated by `bun typegen` and committed.
- `scripts/`: the seed (`seed.ts`, `seed-data.ts`, `register.ts`), the export, the migration runner
  with `migrations/`, the album import (`import-album.ts`, its plan in `album-import.ts`), the query
  tool, and `sanity.sh`, which runs the Sanity CLI with `packages/web/.env` loaded.
- `functions/`: the `enquiry-notify` and `content-lint` Sanity Functions, which
  `sanity.blueprint.ts` at the repo root declares (runbook, Functions).

## Commands

From the repo root. The dataset scripts read `packages/web/.env`.

| Command | Does |
| --- | --- |
| `bun typegen` | extracts `schema.json`, then generates `src/sanity.types.ts` |
| `bun seed` | seeds `development`; `-- --dry-run`, `-- --replace`, `-- --dataset <name>` |
| `bun run export`, `bun run migrate -- <name>` | a dataset export and a migration's dry run (runbook, Migrations) |
| `bun run import-album -- <manifest>` | an album's photographs from a folder: a dry run, then `--apply` uploads the files and saves the album as a draft |
| `bun run --filter @oy/content query -- '*[_type == "zone"]{name}'` | one GROQ query with the Viewer token, no login; `--dataset`, `--perspective drafts`, `--public` |
| `bun run --filter @oy/content sanity -- <args>` | any Sanity CLI command with the env loaded (needs `sanity login`) |
| `bun run --filter @oy/content test` | this package's tests |

The seed creates what is missing, fills missing fields, unsets retired ones and revises a value an
earlier seed wrote while it still reads as that seed wrote it, so an editor's change stays
(ADR 0035). The dataset scripts accept an older `SANITY_WRITE_TOKEN` for `SANITY_API_WRITE_TOKEN`,
with a warning, because the owner's `.env` predates the wizard's names.

## Rules that matter most here

- A required-for-launch field gets its entry in `src/pending.ts` in the same change.
- Stored content changes shape only through a reviewed migration, never by hand in the Studio.
- After a schema or query change, run `bun typegen` and commit both generated files; CI's
  `TypeGen drift` job fails on a difference.

Conventions: the `oy-content-model` skill. Adding content through the Sanity MCP server: the
`oy-content-ops` skill.

## Deltas from the spec

The spec is `docs/design/CONTENT-MODEL.md`. Where the built model differs, an ADR says how and why:

- ADR 0013: facts that change each year live on the `event` edition; `stat`, `door` and
  `governanceDoc` are documents; derived fields are not stored; album credits sit on the album.
- ADR 0015, ADR 0016: an `enquiry` holds one read-only object per kind, and the newsletter writes a
  `subscriber`; routing contacts are entries by role, and the success copy is a template.
- ADR 0024, ADR 0025, ADR 0029: event pages show the next edition, the Gala's Eventbrite link is the
  edition's `ticketsUrl`, and each page keeps its own take-part rows (`takePart[]`, nine ways in).
- ADR 0031, ADR 0034, ADR 0035: the program and trust pages' fields, such as sub-programs with
  photographs and facts, the vendor door, an outcome that names one subject, and a timeline entry
  that is a year and one line.
- ADR 0039: the gallery singleton is `galleryPage`; an album's year comes from its date or edition.
- ADR 0042: members are Editors, and administrators keep the settings and the Inbox (no News page since ADR 0048);
  outcomes, timeline entries, giving levels and initiatives are lists on their pages; one control
  per decision; an input no page reads is deleted, or named in `src/hidden-inputs.ts` if kept.
- ADR 0050: an album holds `videos`, a list of the shared `video` object (a title, the YouTube address, an
  optional still and who made it) that the site plays from YouTube once a visitor presses play; optional, so
  no Pending row and no To do row.
- With no ADR of their own: `cta` has `kind` plus `enquiryKind`; `stat` stores its figure flat
  (`value`, `label`, `source`); `scheduleItem.title` is `bilingual` with English required; and
  `festivalPage.whatItIsImage`, `programsPage.culturalExchange.howToJoin` and
  `siteSettings.newsletterBlurb`, which the prototypes draw, render Pending while empty.

`RETIRED_FIELDS` in `scripts/seed-data.ts` lists the retired fields that the seed and the
`retired-fields` migration unset.
